## 1. 任务清单

| 任务 | 优先级 | 栈 (word) | 阻塞点 | 节拍来源 | 独占资源 | 截止期 |
|:---|:---:|:---:|:---|:---|:---|:---|
| `modbus_task` | **4** | 256 | `xQueueReceive(500ms)` | 指令 + 超时兜底 | USART2 / RS485 | **200 ms 硬** |
| `net_task` | **3** | 512 | `xQueueReceive(500ms)` | 事件 + 超时（心跳检查） | USART1（共享）、ESP8266 | 30 s 软 |
| `sensor_task` | **2** | 256 | 队列满才等 | `vTaskDelayUntil(1000)` | DHT11 / ADC | 无 |
| `storage_task` | **2** | 256 | `xQueueReceive(portMAX_DELAY)` | 纯数据驱动 | SPI2、W25Q64 | 无 |
| `ui_task` | **1** | 768 | 队列读用 0 超时 | `vTaskDelayUntil(33)` | LVGL | 无（掉帧无碍） |
| `monitor_task` | **0** | 160 | 无（周期长） | `vTaskDelayUntil(10000)` | USART1（共享） | 无 |

**优先级依据是【截止期】，不是【重要性】**：

- `modbus` 最高：从站响应窗口 200 ms（`MB_RESP_TIMEOUT_MS`），超时要重发，重发再超时就报错——全系统最紧的一根弦。
- `net` 次之：KeepAlive 半周期（30 s）内必须发心跳，否则被 broker 踢掉。
- `sensor` / `storage` 同级：一个采样一个落盘，都没有硬截止期。同优先级靠时间片轮转公平分享（`configUSE_TIME_SLICING` 未定义，FreeRTOS 默认 1，即开启），**同优先级本身就是一个设计决策**。
- `ui` 最低的正事：**用户能感知 ≠ 有业务后果**。掉几帧画面依然正确（LVGL 画的总是最新状态），而 Modbus 超时会导致数据错。
- `monitor` 最低：纯观测，任何正事都能插队。它同时是**喂狗任务**。

> ⚠️ FreeRTOS 里**优先级数字越大越高**（与部分 RTOS 相反）。
> ⚠️ 栈深度单位是 **word（4 字节）**，不是 byte。
> ⚠️ 当前 `configMAX_PRIORITIES = 56`，合法优先级 0–55；本项目只用到 0–4。

### 为什么是这 6 个，不是 3 个或 10 个

**切分依据是「触发源 + 阻塞特性」，不是「代码模块」。**

| 反例 | 为什么合并/拆分 |
|:---|:---|
| AT 指令 + MQTT 合成 `net_task` | 两个"模块"，但**同一条串口上一问一答，触发源相同**，拆开反而要跨任务同步时序 |
| `storage_task` 单独 | Flash 擦除几十 ms，塞进别的任务会拖累它 |
| `ui_task` 单独 | LVGL 非线程安全，必须单任务独占 |
| `sensor_task` 单独 | 周期最稳定，被网络卡住会丢采集点 |

## 2. 共享资源与保护

| 资源 / 数据 | 机制 | 参数 | 为什么 |
|:---|:---|:---|:---|
| USART1 | **互斥锁** `s_uart1_mutex` | 超时 100 ms | 调试口被 `monitor_task`/`net_task` 共用，物理上无法独占 |
| SPI2 / W25Q64 | **无锁** | — | `storage_task` 单任务独占 → **用架构消灭锁** |
| 传感数据 → 落盘 | 队列 `storage_q` | 深度 16 | 所有权转移；深度 16 用于扛擦除卡 80 ms 的抖动 |
| 传感数据 → 上报 | 队列 `net_q` | 深度 16 | 与 storage 对齐 |
| 最新值 → UI | 队列 `ui_q` | 深度 1 | **`xQueueOverwrite`**，生产者永不阻塞 |
| 命令 → Modbus | 队列 `modbus_q` | 深度 8 | 上位机轮询 + 本地采集，突发最多几条 |
| 网络状态 | `volatile` + getter | — | 单字长读写，无需加锁 |

**锁 vs 队列的语义**：锁保护**资源**（同一资源被并发访问），队列传递**数据所有权**（谁拥有这条数据）。用错不报错，只在特定时机炸。

### 四条加锁规矩

1. **一把锁一个任务**：同一任务最多持有一把锁。
2. **不嵌套**：绝不在持锁期间获取另一把锁（即使当前只有一把，也按"将来会加锁"写）。
3. **持锁不做长阻塞**：`xSemaphoreTake` 超时统一 100 ms；重连退避的 `vTaskDelay` 必须放在**放锁之后**。
4. **持锁不 `printf`**：互斥锁默认**非递归**，在持锁时调 `log_line()` 会**自死锁**。

### 为什么是 Mutex 而不是 Binary Semaphore

`xSemaphoreCreateMutex()` 带**优先级继承**：拿锁的低优先级任务会被临时提升到等待者的优先级，避免被中优先级任务间接拖死（优先级翻转）。二值信号量**没有**这个机制。

### USART1 接线的现状（重要）

当前 `usart.c` 只配置了两路串口：

- **USART1**（PA9/PA10，115200）—— 调试打印口。本项目的 `uart1_mutex` 保护的就是它。
- **USART2**（PA2/PA3，9600）—— RS485 / Modbus 从站。

**ESP8266 的 UART 尚未配置**，W7 接入时需要新增一路串口（USART3 或软件串口）。届时 AT 指令走那一路，`net_task` 需要的独占保护应在 W7 落地时补进本文与代码，**现在不要假设 ESP8266 已经挂在 USART1 上**。

## 3. 数据流图

```
sensor_task (1s)
   │
   ├─► storage_q(16) ─► storage_task ─► W25Q64 环形缓冲 ─┐
   │        (满了丢最旧 + drop_cnt++)                     │
   │                                                     │  net_task 从 Flash 取
   ├─► net_q(16) ─────────────────────────────────────►  │  ① 在线：按节拍发
   │        (满了丢最旧 + drop_cnt++)                     │  ② 断网：只重连
   │                                                     │  ③ 补传：逐条等 PUBACK
   └─► ui_q(1)  xQueueOverwrite ─► ui_task (33ms)         ▼
                                                    ESP8266 ─► 云端 broker
```

**为什么在线/断网都先写 Flash（写缓冲优先）**：
在线和断网用**同一条写路径**，少一个分支就少一类 bug。代价是 Flash 磨损，但 1 条/秒对 W25Q64 完全可接受。
**收益**：`sensor_task` 和 `storage_task` 根本不知道网断了——**故障被限制在 `net_task` 里**。

### 网络三态机

```
        ┌──────────── 连接失败 / 断开 ────────────┐
        ▼                                         │
   NET_OFFLINE ──连接成功──► NET_ONLINE ──有积压──► NET_BACKFILL
        ▲                    (按节拍发)                 │
        └──────────────────── 补完 ──────────────────┘
```

**为什么不能用 `bool is_online`**："连着但还在补传"是一个**真实的中间态**。当 bool 处理 → 补传期间按普通节拍发，积压永远清不完；当离线处理 → 就不该发。**三态是刚需。**

### 环形缓冲与掉电安全

- 游标是**记录序号**（`wp`/`rp`），不是字节地址 → 换页/换扇区时逻辑不用改。
- 空：`wp == rp`；满：`(wp + 1) % N == rp` → **覆盖最旧**。
- **`rp` 只在收到 PUBACK 时才推进** → 发出去就推进的话，发失败这条数据就永远丢了。
- 掉电安全：**先写数据（含 CRC），再更新 `wp`**。顺序反了，掉电会读到半条无效记录。
- 内存中记录 16 B：`timestamp(4) + temp(2) + humi(2) + light(2) + 隐式填充(2) + seq(4)`，由 `_Static_assert` 卡住大小与偏移。
- 落盘记录 32 B（W5 定）：上面 16 B + 预留 + `crc(2)`。
- 补传**窗口 = 1**（逐条等 PUBACK）：天然限速，且不乱序。断网 30 分钟约积压 1800 条，一口气全发会压垮 TCP 缓冲和 broker。

## 4. 关键决策与理由

| # | 决策 | 理由（一句话版） |
|:---:|:---|:---|
| 1 | 按**触发源**切 6 任务 | 模块划分解决不了并发；触发源相同的放一起才不会跨任务同步 |
| 2 | **截止期**排优先级 | "重要"是主观的，截止期是客观的；答不出时限就等于没设计过 |
| 3 | UI 优先级**最低** | 用户感知 ≠ 业务后果；且 LVGL 画的总是最新状态，跳帧画面依然正确 |
| 4 | 数据**先写 Flash 再发** | 在线/断网共用一条写路径，少分支少 bug |
| 5 | 用**队列**不用全局变量 | 全局变量没有同步语义（撕裂）、没有等待能力、没有所有权转移、没有流控 |
| 6 | **三态**而非 bool | "连着但补传中"必须能表达 |
| 7 | 补传以 **PUBACK** 推进 | 发送成功 ≠ 对方收到；只有确认才能保证不丢不重 |
| 8 | 喂狗放 `monitor_task` | IWDG 在调度器启动前就已使能，超时 20 s；10 s 一轮喂狗，余量 2 倍 |

**为什么用队列而不是全局变量**（面试必问，四层）：
1. 全局变量**没有同步语义**：多任务读写会发生撕裂/可见性问题。
2. 全局变量**没有等待能力**：消费者只能轮询空转，浪费 CPU。
3. 全局变量**没有所有权转移**：谁在用、能不能改，全靠约定。
4. 全局变量**没有流控**：队列满了会阻塞，自然把压力反馈给生产者。

一句话：**全局变量是共享内存，队列是消息传递。**

### 喂狗为什么必须单独说

`main.c` 里 `MX_IWDG_Init()` 在 `osKernelStart()` **之前**执行，IWDG 一旦启动就无法关闭：

```
LSI ≈ 32 kHz, 预分频 256, 重载 2499
超时 = 2500 × 256 / 32000 ≈ 20 s
```

删除 CubeMX 的 `defaultTask` 时，必须同时接手它的 `HAL_IWDG_Refresh()` 调用。本项目的做法是把喂狗放进 `monitor_task`（10 s 周期）。**如果只删任务不接手喂狗，板子会每 20 s 复位一次**，而在没有硬件的情况下这种错误只能靠读代码发现。

## 5. 故障隔离视图

| 故障 | 影响范围 | 为什么不扩散 |
|:---|:---|:---|
| ESP8266 掉线 | 只有 `net_task` 忙重连 | 采集/存储/UI 无感，数据继续进 Flash |
| Flash 擦除卡 80 ms | 只有 `storage_task` 延迟 | `storage_q` 深度 16 兜住 |
| Modbus 从站不响应 | 只有 `modbus_task` 等超时 | 200 ms 后重发/报错，不阻塞别人 |
| UI 花了 200 ms 刷屏 | 只丢几帧画面 | 最低优先级，且读的是覆盖式信箱 |
| `printf` 被抢占 | 串口锁保护 | `uart1_mutex` + 优先级继承 |

> **分任务真正的价值不是"并发"，而是"故障隔离"。**
